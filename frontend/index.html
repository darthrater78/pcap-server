Where are the tcpdump flags?

If you are used to typing tcpdump -nnvvXi eth0 port 443, the flags in that command split into two groups, and only one of them is doing what you think.

This tool always runs tcpdump -w <file>, because the point is to bring a pcap back for analysis. -w turns tcpdump from a printer into a writer. It stops formatting text entirely and writes raw packet records to the file. So -v, -vv, -q, -A, -X, -XX, -e, -n, -nn and the -t family have nothing to format and cannot change a single byte of the capture. They are not filtered out here — tcpdump itself ignores them under -w.

-v is the one exception, and this tool adds it to every capture for you — which is why you will see it in the command below. It still changes nothing about the file. Under -w it makes tcpdump report its running packet total on the side, once a second, and that is what the packets so far figure on a running capture is reading. The pcap stays on the remote host until the capture ends, so there is nothing else to count.

Those flags were accepted in earlier builds. That was misleading: you could set them, and nothing happened. They have been removed rather than left as controls that do nothing. The ones that describe how to read a capture now live in the Viewer, where they apply to the packet list and genuinely change what you see.

Exactly four things change what a capture contains, and all four are fields above:

Interface-iwhich link to read from
Max packets-cstop after this many packets
Snap length-sbytes kept per packet — lower it to capture headers only
BPF filterexpressionwhich packets are captured at all

Selecting specific traffic was never a flag's job in tcpdump either — it is the filter expression's. That is the box to reach for, and it takes the full Berkeley Packet Filter syntax:

host 10.0.0.230everything to or from one host
tcp port 443one TCP port, both directions
port 53 and not host 8.8.8.8combine with and, or, not
net 192.168.1.0/24a whole subnet
vlan 100a single VLAN
icmp or arpprotocols by name
tcp[tcpflags] & tcp-syn != 0SYNs only — byte-level matching works too
less 128packets under 128 bytes

Shell metacharacters are rejected in the filter, and the expression is passed to tcpdump as a single quoted argument after --, so a filter can never become part of the command. A small set of flags (-z, -W, -G, -C, -r, -F, -V, -Z) is permanently refused: tcpdump may be running under sudo, and those turn a capture into code execution or file reads as root.

    This is not the same language as the BPF filter on the Capture tab, and that is the single thing most worth knowing here. They run at different times and they are different syntaxes.

    BPF filter
    Capture tab    		 Decides what is recorded. Applied by tcpdump on the remote host as the packets go past. Anything it excludes is gone for good. tcp port 443
    Display filter
    here    		 Decides what you see out of what was already recorded. Applied by tshark when the list is drawn, so it costs nothing to change your mind. tcp.port == 443

    The shape of the difference: BPF says tcp port 443, display filter says tcp.port == 443. Display filters name a protocol field with a dot and compare it with an operator. A bare protocol name on its own also works — dns shows every DNS packet.

    ip.addr == 10.0.0.1either direction, one host
    ip.src == 10.0.0.1from that host only (ip.dst for the other way)
    tcp.port == 443one TCP port, either end
    http or dnscombine with and, or, not
    tcp.flags.syn == 1 and tcp.flags.ack == 0connection attempts
    tcp.analysis.retransmissionwhat Wireshark flagged as a retransmission
    frame.len > 1000numeric comparison on any field
    http.request.method == "GET"string values go in quotes
    dns.qry.name contains "example"contains for substrings, matches for regex
    !(arp or icmp)! negates, brackets group

    &&, || and ! work as well as the word forms. A filter this tool cannot run is reported back with tshark's own message and the position it objected to, rather than an empty packet list — an empty list here always means the filter was valid and nothing matched it.

    Overview

    How this installation stands. Choose a card to open that section.

    HTTPS certificate

    Get a Let's Encrypt certificate and serve HTTPS directly — no reverse proxy, no inbound ports.

    Learn more

    pcap-server proves the domain is yours by creating a DNS record through your DNS provider — about two hundred are supported — so the machine never has to be reachable from the internet. It waits a short delay and then lets Let's Encrypt check, the same way Proxmox and certbot do. Credentials and the certificate's key are stored encrypted under the master key, and renewal is automatic.

    Capture encryption

    Whether captures and SSH keys are encrypted at rest, and with which key.

    Users

    Accounts that can sign in. Every account must set up a second factor.

    SSH keys

    The private keys pcap-server logs in to target hosts with.

    Learn more

    These are your identity to the target hosts, chosen per server on the Servers tab. Upload the private key file (the one without .pub) whose public half is already in that host's ~/.ssh/authorized_keys. Passwords are never used: key authentication is the only method, which is why capturing as a non-root user needs passwordless sudo. Keys are encrypted at rest under the master key.

    Or paste a key

    The whole file, including its BEGIN and END lines. It must be the private half (no .pub) and must have no passphrase — pcap-server connects unattended and has nowhere to ask for one. It is checked here, not later against a host.

    Known hosts

    Each target host's verified identity. Nothing connects to a host until its keys are trusted.

    Learn more

    These are the host's identity — proof the machine answering is the one you meant — not the login keys under SSH keys. Trusting a host pins what it answers with, so an impostor on that address is refused instead of being handed your key. A host can also be trusted from the Trust host button on the server itself.

    A host usually answers with several keys, one per algorithm (ssh-ed25519 is the modern default; ecdsa-sha2-nistp256 and ssh-rsa are kept for older clients). Whichever the two ends negotiate is the one checked, so all of them are stored together and trusted or forgotten as a set. Rescanning re-fetches them and updates the stored time.
